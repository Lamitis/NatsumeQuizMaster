# 跨端同步说明（局域网 + Syncthing）

> 追加需求：参考 Syncthing 实现手机↔电脑同步，用户扫码即可配对。

## 两条同步路径

| 路径 | 适用 | 说明 |
|---|---|---|
| 局域网同步（原有） | 同一 Wi-Fi 下 | `SyncEngine` + UDP 广播/多播/单播扫描发现 + 识别码/扫码配对（含握手确认） |
| Syncthing 同步（新增） | 跨网络、多端 | 经 Syncthing 共享目录持续同步题库/知识库文件 |

## Syncthing 集成方式

- REST 客户端：`lib/services/sync/syncthing_client.dart`（加设备/加目录/状态）
- 后端：`lib/services/sync/syncthing_backend.dart`（扫码配对 + 目录定位）
- 配对载荷：`lib/services/sync/sync_backend.dart` 的 `SyncthingPairPayload`
  （二维码内容 = deviceId + apiKey + folderId）

### 桌面端

捆绑或按需下载 `syncthing(.exe)`（校验 sha256），作为子进程启动，经 REST
（默认 `http://127.0.0.1:8384`，`X-API-Key` 认证）控制；共享目录固定为
`NatsumeQuizMaster数据/`（题库 JSON + 知识库包 + 清单）。

### Android 端

经 gomobile 把 Syncthing 的 `lib/syncthing` 编译成 `.aar`，在进程内跑，暴露
同一 REST 接口与共享目录。原生构建步骤（本仓库只交付 REST 客户端 + 目录监听
契约）。

## 扫码配对体验

复用现有 `sync_qr_view.dart` / `sync_scan_screen.dart`：一端生成二维码
（SyncthingPairPayload），另一端扫 → 互相 `addDevice` + `addFolder`，之后
Syncthing 自动持续同步；App 监听目录变化，经 `KbFileService` /
`BankFileService` 自动导入新文件（按题目内容指纹去重）。

## 局域网同步（实现要点 · 2026-10-30 修订）

真机反馈「同 Wi-Fi 下发现不了设备 / 电脑端出现扫码界面 / 临时码显示已配对却连不上」，
据此重写了发现与配对两层，界面上也补了平台适配与诊断入口。

### 发现通道（三路并用，缺一不可）

| 通道 | 端口 | 作用 |
|---|---|---|
| 子网单播扫描（主力） | UDP → 对端 51620/51621 | 逐台扫描各网段主机，单播属于出站流量，不受入站防火墙规则限制 |
| 多播信标（辅助） | UDP 51622（组 `239.192.93.93`） | 广播不可达时的备用通道 |
| 广播信标（辅助） | UDP 51620（定向）+ `255.255.255.255`（兜底） | 部分平台「发送不报错但包不达」，故排在定向广播之后 |

- 绑定后**立即** `broadcastEnabled = true`：Windows 上未开启就向 `255.255.255.255`
  发送，`dart:io` 会异步报错并销毁 socket（`send` 看似成功、包其实没发出）。
- 网卡选择统一走 `lib/services/sync/lan_address.dart`：过滤回环 / APIPA /
  CGNAT，识别 VMware / Hyper-V / Docker / VPN / 蓝牙等虚拟网卡，按分排序、
  真实网卡优先。二维码里的 IP、虚拟网卡判断、`/24` 广播与主机列表推算都由它决定，
  避免把 `VMnet1` 的地址写进二维码。
- socket 被系统关闭后自动重建（统计里的「socket 重建」次数）。

### 配对状态机（`SyncPairState`）

`none → awaitingPeer → verifying → verified / rejected`

- 只有向对端 `GET /sync/info` 带码请求拿到 **200** 才置 `verified`（界面才显示「已配对」）；
  403 = 码不对 / 临时码过期 → `rejected`；连不上 → `awaitingPeer` + 8 秒自动重试。
- 握手同时充当连通性探针：200 就证明 IP / 端口 / 防火墙这条链路是通的。
- 已确认的对端地址会被记住，发现通道被挡住时「立即同步」仍可直连。

### 双向握手（v1.35.4）

真机反馈：A 输入 B 的识别码后 A 显示「已配对」，此时在 **B** 上点「立即同步」，
B 却提示「必须输入对端识别码才行」——配对只有单向，B 根本不知道 A 的存在。

现在 A 核实通过后（`/sync/info` 返回 200）立刻追加一次 `POST /sync/pair`：

| 方向 | 内容 |
|---|---|
| 请求头 | `X-Sync-Code: <B 的设备码>` —— 证明 A 确实知道 B 的识别码，B 侧门禁照旧 |
| 请求体 | `{device_id, device_name, code: <A 的设备码>, port: <A 的同步端口>}` |
| B 侧动作 | 记下 A 的码与地址 → 状态置 `verified` → 回 `{ok, device_id, device_name}` |
| 结果 | **双方同时显示「已配对」**，任一方都能直接点「立即同步」 |

安全边界：B 只有在 A 出示了 B 自己的识别码（门禁 200）时才接受配对请求；
B 回包**不含自己的码**，因此第三方拿到配对请求也换不到任何凭据。
配对结果落库（settings 键 `sync_pair_v1`），重启后恢复，但**状态先落回
`awaitingPeer`**，重新核实成功才显示「已配对」（不做乐观 UI）。

### 未配对同步的拦截（v1.35.4）

- UI：`peerConfirmed == false` 时点「立即同步」直接弹提示，**不发任何请求**。
- 引擎：`manualSync()` / `syncWith()` 同样有门禁，返回
  `SyncErrorCode.notPaired`（业务错误），不再让底层用 30 秒超时去兜底。
- 旧表现（已修复）：界面转圈 30 秒后弹 `TimeoutException`（用户看到的「时间溢出异常」）。
  现在所有失败都翻译成 `SyncException`：`notPaired / unauthorized / timeout / cancelled /
  peerUnreachable / payloadTooLarge / badSnapshot / busy / database / unknown`。

### 增量同步（v1.35.4）

每次同步不再是「整库全传」：

- 请求头 `x-sync-since: <ISO8601>`：告诉对端「我已有到这个时刻的数据」，对端只回增量。
- 本机推送同样按 `exportSnapshot(since:)` 过滤：题目按 `updated_at`、配图**跟着题目**
  （只 base64 编码变更题目的图）、作答记录按 `answered_at`、错题按 `added_at`、
  批注按 `updated_at`、笔记/待办按 `updated_at`。
- **题库行始终全带**（体量小，且题目要靠 `bank_uid → 本地 id` 映射）。
- 游标落库（`sync_cursors_v1`），push / pull 各一条；回退 **10 分钟重叠窗口**
  （`SyncRepository.cursorOverlap`）容忍时钟差与同步途中的写入。
- 增量轮次**跳过同名题库内容比对**：只带部分题目会让指纹比对失真、凭空造冲突。
- 后悔药：「网络诊断 → 重置同步进度（下次全量）」会清空游标；
  解除配对时也会自动清空。

### 取消同步 / 不再无限转圈（v1.35.4）

| 机制 | 说明 |
|---|---|
| 步骤超时 | 单次交换 45 秒（`SyncEngine.exchangeTimeout`）；服务端处理上限 120 秒 |
| 看门狗 | 90 秒未收尾强制断链，再过 5 秒硬复位 UI 状态 |
| 用户取消 | 同步中显示「取消同步」按钮 → `close()` 在途连接 → `POST /sync/cancel` 通知对端复位 |
| 服务端忙 | 同时只处理一次交换，并发回 `409 busy`（两端同时点不会互相拖死） |
| 错误语义 | 403/409/413/499/504 全部带 `code` 字段，客户端翻成中文提示 |

### 同步极慢的两个根因（v1.35.4，已修）

1. **嵌套 `db.batch` 死锁**：`importSnapshot` 在事务里调 `mergeQuestionImages`，
   后者走全局 `db.batch()`；同一个连接上的「事务外操作」会排队等事务结束，
   而事务在等它 → 永久挂起（真机表现：日志只有「接收异常」，界面一直转圈）。
   现在配图直接用 `txn.insert`，并把「本地 uid → id」一次性预读，去掉每条记录的单独查询。
2. **每次都全量重传**：几十道题带几 MB base64 配图，每次同步都编码+传输一遍。
   现在按游标增量，未变更题目的配图一张都不编码。

排查顺序（同步慢时）：先看 `[SYNC]` 日志里的步骤耗时（生成快照 / 序列化 /
发送并等待对端 / 接收数据 / 合并数据），再对照「网络诊断」里的收发计数与端口。

### 端口与防火墙

- TCP 51630-51632：同步服务（`/sync/info`、`/sync/pair`、`/sync/cancel`、`/sync/exchange`）
- UDP 51620-51622：设备发现
- Windows 安装包 `tools/natsume_setup.iss` 在管理员安装时自动放行上述端口与程序；
  非管理员安装由应用首次运行时的系统防火墙弹窗处理。

### 平台自适应 UI

- 桌面（Windows / Linux / macOS）：设置页直接展示**本机二维码 + 本机识别码 + 手动输入框**，
  不出现「扫码」按钮；误入扫码页会看到「电脑端没有摄像头」的说明页。
- 手机（Android / iOS）：提供「扫码配对」按钮 + 手动输入框。
- 设置页「网络诊断」展开可查看已发/已收包数、监听端口、参与发现的网卡、最近一次错误。
